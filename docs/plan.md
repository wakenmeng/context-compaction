## 背景

论文 [You don't need long context](https://arxiv.org/pdf/2611.05306)（NVIDIA，2026-11-03）说明：前沿模型靠频繁压缩和按需读取，就能在短上下文下保持接近基线的准确率。

### 论文术语

| 术语 | 含义 |
| --- | --- |
| FHA | 全历史累积，默认不压缩 |
| EoCC | 接近阈值时生成压缩内容，再开新对话 |
| SAC | 每个动作后更新语义状态，再开新对话 |
| 48K/36K | 总上下文上限 / 压缩阈值 |
| Peak length | 最长一段对话的长度 |
| Total length | 所有子对话最终长度之和 |

### 证据强弱

- **较强：** 按需读取能明显减少长输入任务的 token 用量。
- **中等：** EoCC 在所测模型和 benchmark 上接近基线。但 SWE-bench 基线的峰值中位数只有 18–32K，很多任务本来就不长。
- **较弱：** 估算零售成本的节省倍数。模型用开放权重的解码吞吐推算闭源模型的输入和输出价格，而且假设服务商按短窗口降价。
- **未验证：** 完整历史日志加检索、多 agent 场景、人机协作，以及 SSSM。

### 论文留下的空白

1. **多次压缩会累积损失：** 论文承认这一点，但压缩方案仍是每次生成一份文本。
2. **遗漏无法自检：** 模型不知道自己忘了什么，检索工具解决不了这个问题。
3. **缺少充分性指标：** 论文只看最终成功率，没有测量压缩状态能否替代完整历史做决策。

### 核心判断

好的压缩是在逼近 Markov state：给定状态和可访问的环境，下一步决策不再依赖完整历史。环境里能取回的内容，状态里只需保留指针。

这是设计动机，不是实验要证明的命题。实验只检验任务层面的近似充分：在同样的任务和环境访问权限下，压缩后继续执行的成功率不明显下降，重复工作减少，成本不上升。下一步决策一致只用于诊断，不能证明状态充分。

## 目标与成功标准

第一轮回答两个问题：同样的 100 题下，方案 C 是否优于论文 EoCC 提示词 B；弹性上下文 E 是否值得额外费用。

### 假设

- **H1：** C 的成功率不低于 B。
- **H2：** C 的压缩后重复动作率低于 B。定义和三档判定见“H2 的计算”。
- **H3****（诊断）****：** C 的决策一致率高于 B。只用于解释结果，不参与成功判定，原因有三：同样有效的动作可能不同；全历史里的干扰可能让完整历史反而决策更差；丢失的信息可能几步之后才用到。
- **H4：** Σ费用C / Σ费用B ≤ 1.10。费用包含全部调用，口径见“费用计算”。
- **H5：** E 比 C 净多解至少 3 题（仅 E 通过的题数减去仅 C 通过的题数），且 Σ费用E / Σ费用C ≤ 1.20。扩容记录和失败原因分类只用来解释，不作为因果证据。

### 成功标准

| 结果 | 条件 | 下一步 |
| --- | --- | --- |
| 成功 | H1、H2、H4 都成立 | 做消融实验，扩大样本 |
| 证据不足 | H1、H4 成立，H2 为“证据不足” | 扩大样本后再判，不停止这个方向 |
| 部分成功 | H2 成立，但 H1 或 H4 不成立 | 分析原因，调整设计后再测 |
| 失败 | H2 不成立；或 H2 为“证据不足”且 H1 或 H4 不成立 | 停止这个方向，写清楚原因 |

100 题的统计能力有限，H1 的判定采用“不明显更差”：C 比 B 少解的题数不超过 3 题。这个阈值是实验前的约定，只是筛选标签，不等于证明了非劣，也不是统计显著性结论。成功率和题数都在排除“环境不可解”的题之后计算（见“抽样”）。

H1、H2、H4 判断状态压缩本身，H3 只做诊断，H5 单独判断弹性上下文。H5 成立时，产品默认采用“软上限 + 临时扩容”；不成立时，保留固定上限。

- 不跑 FHA 基线 A，也不跑去掉检索的消融组 D。
- 不训练 SSSM，不改模型。

## 系统设计

方案 C 由五个组件组成：完整事件进入日志，模型只提交状态 patch，校验通过后才组装下一轮上下文。

达到 12K 时触发压缩；只有校验通过的 patch 才能生成新状态。需要细节时，模型用 HistoryTool 查询 EventLog。

### 组件

| 组件 | 职责 | 关键约束 |
| --- | --- | --- |
| EventLog | 记录每个动作、结果和模型调用 | 只追加，由容器外的 harness 保存在宿主机上，不挂载进容器，模型无法修改 |
| StateStore | 保存当前状态和历史版本 | 每次变更都生成新版本 |
| Compactor | 请求 patch，校验并应用 | 失败时重试 1 次，再失败走回退 |
| ContextAssembler | 组装下一轮消息 | 稳定内容放前面，保住前缀缓存 |
| HistoryTool | 查询 EventLog | 在容器外执行，只读，只返回有长度上限的片段 |

### 状态 schema

```json
{
  "schema_version": 2,
  "state_version": 7,
  "task": "原始任务全文，由 harness 写入",
  "done_when": ["完成条件"],
  "constraints": [
    {"id": "c1", "text": "已确定的约束", "reason": "原因"}
  ],
  "facts": [
    {
      "id": "f1",
      "text": "事实",
      "status": "observed",
      "sources": ["e17"],
      "at_event": "e17",
      "files": ["src/a.py"]
    },
    {"id": "f2", "text": "旧事实", "status": "superseded", "superseded_by": "f1"}
  ],
  "changes": [
    {"path": "src/a.py", "summary": "改动", "verified": false}
  ],
  "checks": [
    {
      "id": "k1",
      "command": "pytest tests/test_a.py",
      "result": "failed",
      "status": "valid",
      "sources": ["e21"],
      "at_event": "e21",
      "files": []
    }
  ],
  "dead_ends": [
    {"id": "d1", "approach": "失败方案", "reason": "失败原因", "at_event": "e19", "files": ["src/a.py"]}
  ],
  "plan": ["按顺序排列的子目标"],
  "next_action": "紧接着要执行的命令或修改",
  "pointers": [
    {"label": "完整错误日志", "ref": "e21"},
    {"label": "要改的函数", "path": "src/a.py", "symbol": "parse_header"}
  ],
  "fallback_recap": null
}
```

### 字段权限

| 字段 | 修改权限 | 规则 |
| --- | --- | --- |
| `task` | 仅 harness | 永不改写 |
| `done_when` | 模型 | 首次压缩时创建，之后只能追加 |
| `constraints` | 模型 | 可增改，必须有 `reason` |
| `facts` | 模型 | status 取 observed、verified、assumed、stale 或 superseded；observed 和 verified 必须带 sources、at_event 和依赖的 files；被推翻时标为 superseded 并写 superseded_by，不直接删除 |
| `changes`、`checks` | 模型 | 可增改；checks 必须带 at_event 和 files，status 取 valid 或 stale，只有 harness 能标 stale |
| `dead_ends` | 模型 | 只能追加；状态超限时才允许合并 |
| `plan`、`next_action` | 模型 | 可覆盖，不能为空 |
| `pointers` | 模型和 harness | 两类引用不混用：历史证据用 ref 指向事件 ID，永不改变；环境引用用 path 加可选的 symbol，不写行号，用到时重新读取。ref 必须能在日志中解析，path 必须是仓库内的相对路径 |

### 失效规则

增量更新能减少旧事实被意外改写，但也会让过期的事实和验证长期留在状态里，比如代码改了之后，“测试通过”已经不再成立。“增量更新能减少信息衰减”是待验证的假设，不能预先当成收益。以下规则由 harness 用程序执行，不额外调用模型：

- harness 按内容哈希记录每个事件改动了哪些文件，不依赖模型自己报告。
- 如果一条 fact 或 check 的 files 在它的 at_event 之后被改动过，harness 自动把它标为 stale，原文保留。
- 组装上下文时，stale 和 superseded 的条目带标注排在后面；模型重新验证，并给出新的 sources 和 at_event 之后，才能改回 observed 或 verified。
- dead_ends 也记录 at_event；依赖的文件变了之后，只提示模型“这条失败方案的前提可能已经变了”，不自动删除。
- stale 标记次数、重新验证次数计入过程指标。
- 恢复有效时，新 sources 里至少要有一个事件晚于标记 stale 的那个事件，并且是一次观察或检查（读文件、跑命令）；所有 sources 都不能晚于 at_event。
- check 的 files 可以为空，表示依赖整个仓库：仓库里任何文件被改动都会把它标为 stale。跑测试一类的 check 默认按这种保守方式处理。
- fact 的 files 为空，表示它不依赖仓库文件（比如环境里的包版本）。空依赖的比例计入过程指标。
- 这些规则只保证对声明的依赖做机械失效，不验证事实本身是否为真，也不保证模型没有漏填依赖。

### Patch 协议

模型在压缩轮只返回 JSON，不调用工具。论文的压缩提示词依然保留，用来说明压缩目的，但输出格式改成 patch：

```json
{
  "base_version": 7,
  "ops": [
    {"op": "add", "field": "facts", "value": {"id": "f8", "text": "...", "status": "observed", "sources": ["e33"], "at_event": "e33", "files": ["src/b.py"]}},
    {"op": "update", "field": "facts", "id": "f3", "value": {"status": "verified", "sources": ["e34"], "at_event": "e34"}},
    {"op": "update", "field": "facts", "id": "f2", "value": {"status": "superseded", "superseded_by": "f8"}},
    {"op": "set", "field": "next_action", "value": "python -m pytest tests/test_a.py"}
  ]
}
```

`remove` 只在超限缩减时允许，而且只能移除 superseded 和 stale 的条目。

校验器拒绝以下情况：

- `base_version` 不匹配
- 修改 `task`，或违反字段权限
- `observed` 或 `verified` 事实缺少有效来源
- `next_action` 或 `plan` 为空
- 引用不存在的事件
- 应用后状态超过上限（处理见下文）
- observed 或 verified 事实、check 缺少 at_event 或 files
- 模型把条目标为 stale，或把 stale 条目改回有效但没有新证据
- 环境引用带行号，或 ref 不是事件 ID

校验失败时，把错误信息发回模型重试 1 次。仍然失败就走回退：用论文提示词生成文本交接，写入 `fallback_recap`，上限 3K。回退后的上下文只注入 fallback_recap，不再同时注入旧状态，这样不会超过状态上限；旧的有效版本留在 StateStore 里。因为模型看不到旧状态，回退后的下一次压缩是重建轮：模型输出一份完整状态（不是 patch），用同样的 schema 和校验规则检查，task 仍由 harness 写入。重建成功后清空 fallback_recap，失败则再次回退。回退和重建次数都计入结果。

重建轮是一个新的状态周期，不是对旧版本的 patch：

- task、done_when、constraints 由 harness 从最后一个有效版本原样带入，并在重建提示里展示给模型。模型只能追加，不能删改，和平时的字段权限一致。
- facts、changes、checks、dead_ends、plan、next_action、pointers 由模型重新给出，允许遗漏旧条目；“只能追加”和“不能直接删除”只在同一周期内生效。
- 重建出的 fact 和 check 必须满足同样的来源规则。harness 按各自 at_event 之后的文件改动重新计算 stale，所以换一个 ID 不能让已失效的事实恢复有效。

状态超过上限时，拒绝信息里给出当前大小和上限，要求模型提交一个缩减 patch，顺序是：先把 superseded 和 stale 的条目移出当前状态（历史版本里仍然保留），再合并 dead_ends，最后精简 facts 的文字。task、done_when、constraints 不能删。缩减和校验失败的重试共用同一次重试额度，缩减后仍然超限就走回退。缩减次数计入过程指标。

### 触发和上下文组装

16K 硬上限只用于 B、C 的实验配置，E 组规则见下文。上下文两次压缩之间正常累积历史，只在压缩后重置。压缩后的下一轮消息按以下顺序组装：

1. 系统提示和工具说明
2. 任务原文
3. 当前状态 JSON
4. 最近 2 个事件，内容受工具输出上限约束

状态初始上限设为 3K token，最近事件窗口设为 2。这两个值是初始假设，冒烟时允许调整，正式实验开始后冻结。

**Token 计数和越界处理**（三组共用）：

- 用模型官方 tokenizer 计数。上下文长度指一次调用的全部输入，包括系统提示和工具说明；输出上限包含推理 token。
- 普通轮：加入最新工具结果后，输入超过 12K 时改发压缩轮；否则输出上限 = 16K − 输入（含推理 token）。输出因到达上限被截断时，按 mini-swe-agent 的格式错误处理：不执行命令，返回统一的错误提示，计入步数。
- 压缩轮：输入 = 当前上下文 + 压缩提示；输出上限 = 16K − 输入。剩余输出空间不足 1K 时不发调用，直接记为 `context_overflow`。输出被这个上限截断时：patch 或重建算一次失败的尝试，按重试和回退流程处理；文本交接也被截断，则记为 `context_overflow`。重试和回退调用用同样的计算。压缩提示不重复上下文里已有的状态，只给出版本号和 stale 条目（2026-11-04 修订，见变更记录）
- 压缩后重置：新上下文（系统提示、任务、状态或文本交接、最近事件）必须 ≤ 12K。超出时先逐个去掉最近事件；仍然超出就记为 `context_overflow`。B 的文本交接同样受这条约束。
- 单个工具结果过大：B 沿用 mini-swe-agent 原版的截断，C、E 用 4,000 字符上限；截断后压缩轮仍然放不下，就按上一条处理。三组都用这套规则，只是截断方式不同，差异写进报告。

### 工具输出和历史检索

- 单次工具输出进入上下文的上限：4,000 字符。
- 超出部分保留在日志里，并在结果中返回事件 ID。
- 完整日志由容器外的 harness 写入宿主机的 `results/<group>/<instance_id>/events.jsonl`，不挂载进容器，因此不会污染 `git diff` 提交的 patch，模型也无法用 shell 读写。
- 每次动作后由 harness 写日志；`hist` 是 harness 在容器外实现的只读接口，模型只能通过它读取有长度上限的片段。
- agent 只能看到 `problem_statement` 和容器里在 `base_commit` 上的仓库。`patch`、`test_patch`、`FAIL_TO_PASS`、`PASS_TO_PASS`、`eval_script`、`hints_text` 只留在评测侧；数据快照和 `results/` 都不挂载进容器。
- `hist search <regex>`：返回匹配事件及行号。
- `hist read <event_id> --lines A:B`：读取有界片段。

### 回退和停止条件

| 情况 | 处理 |
| --- | --- |
| Patch 解析或校验失败 | 重试 1 次，再失败使用文本交接 |
| 压缩轮超过 16K 上限 | B、C 终止对话并提交当前结果；E 自动扩容，扩容额度用完后同 B、C。都记录为 `context_overflow` |
| 连续 3 次回退 | 继续运行，但标记该题，分析时单独报告 |
| 达到步数或费用上限 | 终止并提交当前结果，记录原因 |
| 运行期基础设施故障（镜像、容器、网络、API 错误） | 各组按相同条件最多重试 2 次；仍失败记为未解决，并做排除这些题的敏感性分析。不按组挑题删除或补跑 |

B、C、E 共用同样的步数和单题费用上限。

### 弹性上下文（E 组）

E 组以 16K/12K 为常态，只有在分块读取解决不了时才临时扩容，这一步结束后写回状态并压回常态。

**触发条件：**

1. 压缩轮本身放不下时，由 harness 自动扩容，防止任务直接失败。自动扩容和模型主动申请共用每题 3 次的额度。
2. 模型调用 `ctx expand <48K|128K> --reason <原因>`，用于必须同时查看的大内容，比如大文件比对或大范围重构。
3. 同一日志片段被 `hist read` 读取 3 次以上时，harness 提示模型可以申请扩容，但不自动执行。

**规则：**

- 扩容档位依次是 48K/36K 和 128K/96K（硬上限 / 压缩阈值，沿用 16K/12K 的 3/4 比例），不超过模型窗口。扩容期间按三组共用的 token 规则执行，只是换成当前档位的数值；工具输出上限放宽到 16,000 字符。
- 每题最多扩容 3 次（含自动扩容），超过后拒绝并记录；额度用完后压缩轮放不下时按 B、C 的 `context_overflow` 处理。退出扩容时压缩失败，就按校验失败的流程重试和回退。
- 每次扩容最多持续 5 个动作，或在模型调用 `ctx release` 时结束。
- 结束时在当前档位的预算内走一次正常 patch 压缩。压缩后的重置输入 ≤ 12K 才回到 16K/12K；否则按回退处理，回退后仍超出就记为 `context_overflow`。自动扩容只用来完成这一次压缩，完成后立即按这条规则退出。
- 申请原因写入日志，方便事后判断扩容是否必要。

这些数值是初始假设，冒烟后冻结。

正式实验是配对比较：B、C、E 使用相同的 100 题、模型和步数上限；B、C 固定 16K/12K，E 以此为常态并允许临时扩容。

| B | 论文 EoCC | 文本交接 | 沿用 mini-swe-agent 默认 | 无 |
| C | Markov 状态压缩 | 状态 patch | 4,000 字符，完整内容进日志 | 有 |
| E | Markov 状态压缩 + 临时扩容 | 状态 patch | 常态同 C；扩容期间 16,000 字符 | 有 |

- **策略差异：** 压缩提示词和输出格式、工具输出截断方式（B 沿用 mini-swe-agent 原版）、是否有 `hist` 和 `ctx`。

### 抽样

1. 数据：`SWE-bench/SWE-bench_Verified` 固定 revision `78f471bf` 的 500 题。swebench 5.x 评测需要它的 `image`、`eval_script` 字段；它与 princeton-nlp 版的 ID、题面、补丁完全相同，仅 2 题的 PASS_TO_PASS 有删减。agent 和评测读同一个本地快照。
2. 正式集 100 题：按仓库分层，种子 `20261104`，配额用随机化系统取整，每题入样概率都是 1/5，简单平均是 500 题成功率的无偏估计。单次样本里 Flask、Seaborn 为 0 题，属于抽样波动。
3. 冒烟集 20 题：从剩余 400 题中抽，每个仓库先抽 1 题，其余按比例分配；本次覆盖全部 12 个仓库。
4. 冒烟题只用于调参和环境验证，不进入正式结果，避免调参污染。
5. 题目列表和全字段指纹 `records_sha256` 写入 `configs/instances.json` 并提交，之后不再更改。
6. 环境验证：用 gold 补丁对 120 题跑官方评测。没通过的题再重跑 2 次，仍不通过就列入 `configs/env_unsolvable.json`，跑 agent 前冻结。这些题在所有组的主分析中统一排除，另报告包含它们的结果。
7. 扩大样本（“证据不足”时）：本轮结论只基于这 100 题，独立报告；扩样是下一阶段。开始前先登记种子、题数、合并分析的判定阈值、扩样次数和停止规则；新题从未入选的 380 题中用同样的分层方法抽取，先按第 6 条完成 gold 验证并冻结排除名单，再跑 agent。

| 配对差异 | 仅 B 通过、仅 C 通过的题数 | H1 |
| 重复动作率 | 压缩后窗口内的重复动作数 / 窗口内动作数，定义见“H2 的计算” | H2 |

### H2 的计算

- **动作：** agent 发出的一次 shell 命令，包括对 stale 条目的重新验证。按下面“重复”的定义，重新验证时依赖的文件已经变了，所以不会被算成重复。压缩轮、patch 重试、`hist` 和 `ctx` 命令不算动作，分子分母都不计入，以免 C 特有的命令稀释它的重复率。重新验证次数另外作为过程指标报告。
- **归一化：** 去掉多余空白，工作目录相同；参数顺序不同视为不同命令。归一化脚本在 M2 写完并冻结，之后不改。
- **重复：** 归一化后与压缩前某条命令相同，并且从那条命令到现在，harness 记录的仓库文件哈希都没变。不分析命令读了哪些文件，仓库有任何改动就不算重复，这样对 B 和 C 的误差方向相同。
- **窗口：** 每次压缩后的 10 个动作；窗口重叠时每个动作只算一次；任务提前结束时只算已发生的动作。
- **样本：** 只统计 B 和 C 都至少压缩过 1 次、且压缩后都有窗口动作的题；其余题记为无暴露，报告题数，不进入 H2。有效题少于 10 题时，H2 直接判为“证据不足”。
- **统计量：** 汇总重复率 = Σ重复动作 / Σ窗口动作，分组计算；差值 = C − B。同时报告每题的重复次数和窗口动作数。
- **判定：** 在有效题上按题配对重采样 10,000 次。差值的 95% 置信区间上界 < 0 为“成立”；点估计 < 0 但区间跨过 0 为“证据不足”；点估计 ≥ 0 为“不成立”。重采样中任一组分母为 0 的样本丢弃，并报告有效次数；有效次数低于 9,500 时判为“证据不足”。

### 费用计算

- 所有组用同一份价格表，在 M3 冻结并写入配置。
- 计入该组运行中的全部模型调用：普通轮、压缩轮、无效 patch、重试、回退、缩减、扩容期间的调用，输出侧包含推理 token。
- 不计入诊断调用（决策回放、裁判），它们单独记账。
- H4、H5 的费用比都是同一题集上的 Σ费用比，排除“环境不可解”的题；配对重采样直接给出费用比的 95% 置信区间。

### 决策一致率

这个测试只做诊断，不参与成功判定，也不用来调整状态设计。它只生成下一步、不执行动作，所以可以用日志离线回放。

1. 从 B 和 C 的正式运行中，分层抽取 30 题，每题最多取 3 个压缩点。
2. 用日志构造压缩点时的完整历史 `H`。
3. 取该组实际使用的压缩上下文 `S`。
4. 对 `H` 采样 2 次，得到 `H1`、`H2`；对 `S` 采样 1 次，得到 `S1`。
5. 判定 `H1` 与 `H2` 是否等价，得到噪声底线。
6. 判定 `H1` 与 `S1` 是否等价，得到决策一致率。
7. 比较 B、C 相对各自噪声底线的差距，以差距更小者为优。

等价判定使用模型裁判。裁判只看任务、两个动作和判定标准，不知道动作来自哪一组；样本随机打乱，并人工抽查 20 条。标准是：**目的相同，且作用于相同目标**。命令写法不同不算差异。

完整历史超出模型窗口的压缩点直接跳过，并报告覆盖率。回放提示、工具定义、采样参数在 M5 之前冻结。裁判可以判“不确定”，不确定的样本单独报告，不计入一致率。

### 统计方法

- 成功率：报告配对差异、McNemar 精确检验，以及 95% 配对 bootstrap 置信区间。
- 费用：配对重采样直接计算 Σ费用比的 95% 置信区间。
- H2：按“H2 的计算”。
- 其他连续指标：按题配对计算差值，用 10,000 次 bootstrap 给出 95% 置信区间。
- 所有区间只针对这 100 题，是探索性的配对比较，不外推到 500 题总体。
- 不声称“显著优于”，除非置信区间支持。
- 只跑 1 次，不做多次重复；如果冒烟显示波动很大，再讨论是否增加重复次数。
- 主要比较是 B 对 C，E 对 C 是次要比较。决策一致率回放只做 B 和 C，E 的分析重点是扩容记录。

- `states/`：每个状态版本
- `compactions.jsonl`：压缩请求、响应、校验结果、是否回退
- `usage.json`：新输入、缓存输入、输出 token 和费用
- `patch.diff`：最终提交
- `eval.json`：官方评测结果
- `run.json`：配置哈希、代码 commit、模型名、开始和结束时间

## 风险与预算

最大风险不是模型费用，而是环境差异和样本太小导致结论不可靠。

### 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| Mac ARM 环境失败或缓慢 | 结果缺失，运行时间过长 | M3 验证，M4 用 10% 失败率判断是否切换 x86 |
| B 与论文配置不同 | 不能与论文数字直接比较 | 只做 B 与 C 的内部比较，公开所有差异 |
| 工具输出上限影响成功率 | 分不清差异来自状态还是输出上限 | 记录 `hist` 调用和截断次数；如 C 胜出，下一轮做消融 |
| 状态 JSON 过大 | 压缩频率上升，工作空间不足 | 监控状态 token，冒烟时调整上限 |
| Patch 频繁失败 | 退化成文本交接，实验失去意义 | 回退率超过 10% 时修 schema 或提示词，再冻结配置 |
| 过度调参 | 冒烟结果无法外推 | 调参只用 20 题冒烟集，只看成功率、回退率和状态大小，不以决策一致率为目标；正式配置冻结后不再修改 |
| 费用超支 | 中途停跑 | 设置单题和总费用上限，每 20 题检查一次 |
| 泄露评测信息 | 结果失真 | 模型看不到隐藏测试和其他组结果；日志目录隔离 |
| E 组扩容过多 | 退化成长上下文，费用升高 | 限制次数和时长；冒烟时检查原因；模型滥用时收紧触发规则 |

### 预算估算

估算基于论文 16K/12K 的名义费用，假设 C 的费用接近 B，E 约为 C 的 1.2 倍。

| 项目 | GPT 5.6 Sol | Opus 4.5 |
| --- | --- | --- |
| 单题费用（论文折算） | $0.41 | $0.63 |
| 正式实验（B、C 各 100 题） | $81 | $125 |
| 正式实验（E 组 100 题） | $49 | $75 |
| 冒烟实验（三组各 20 题） | $26 | $40 |
| 决策一致率回放（粗估） | $30 | $60 |
| 30% 预留 | $56 | $90 |
| **合计** | **约 $242** | **约 $390** |

决策回放和 E 组的费用没有论文依据，要在冒烟后重新估算。论文使用完整 500 题，100 题子集的单题费用可能不同。

### 报告模板

M6 的报告至少回答以下内容：

- **结论：** H1、H2、H4、H5 各自是否成立，属于成功、部分成功还是失败；H3 作为诊断单独报告。结论只限于任务层面的近似充分，不声称验证了 Markov 性。
- **结果表：** B、C、E 的成功率、配对差异、名义费用和实际成本，B、C 的重复动作率和决策一致率，E 的扩容情况。
- **过程诊断：** 压缩次数、回退率、状态大小、stale 和超限缩减次数、hist 使用和缓存命中率。
- **失败分析：** 列出仅 B 通过和仅 C 通过的题目，归类原因。
- **收益归属：** C 相对 B 同时改变了状态结构、字段 patch、失效规则、工具输出上限和日志检索，结论只适用于整套方案，不归因于单一组件。
- **环境说明：** 版本、配置、GCP x86 云主机环境、gold 不通过的题，以及与论文的差异。
- **局限：** 样本量、单次运行、只测一个模型、只测 SWE-bench；100 题适合筛选方向，几题之差不足以支持“无损”结论。
- **下一步：** C 胜出时，按事先登记的顺序做消融：先去掉日志检索（D），再比较结构化整体重写与字段 patch；之后再考虑工具结果清理基线、隔离续跑、Terminal-Bench 或增加模型。
