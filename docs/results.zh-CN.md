## 主要结果

| 组 | 解决 | 95% Wilson 区间 | 费用 | 每题 |
| --- | --- | --- | --- | --- |
| C，16K/12K，预登记 | 82/100 | 73.3%–88.3% | $26.54 | $0.27 |
| C，16K/12K，溢出的题用 24K/18K | 85/100 | 76.7%–90.7% | $30.45 | $0.30 |

第二行把“16K，压缩放不下时用 24K”当作一个策略：在 16K 下跑完的 92 道题保留原结果，溢出的 8 道题用 24K 重跑的结果，两次运行的费用都计入。哪些题换到 24K 只取决于是否溢出，与测试结果无关。这个合并是在 16K 结果出来之后定义的，所以和预登记的那一行并列报告，而不是取代它

### 与论文对比

同一模型、同一份标价；论文用的是全部 500 题，提示词和 harness 都是它自己的

| 设置 | 解决 | 每题 |
| --- | --- | --- |
| 本项目，压缩，16K，放不下时用 24K | 85%（100 题） | $0.30 |
| 本项目，压缩，只用 16K | 82%（100 题） | $0.27 |
| 论文，不压缩（完整历史） | 84.4% | $0.34 |
| 论文，文本交接压缩（EoCC）48K/36K | 88.8% | $0.37 |
| 论文，文本交接压缩（EoCC）32K/24K | 85.0% | $0.37 |
| 论文，文本交接压缩（EoCC）24K/18K | 85.0% | $0.38 |
| 论文，文本交接压缩（EoCC）16K/12K | 84.6% | $0.41 |

**结论。** 论文里压缩从 32K 到 16K 都保持完整历史的准确率（84.6–85.0%），48K 更好（88.8%）。上下文限制在 16K 时，结构化压缩加 24K 兜底同样达到 85%，每题费用是表中最低的，也没有让 agent 重复干活。这是外部对比：区间宽约 ±7 个百分点，样本也不同，所以只能说明“持平”，不能说明“更好”。在同一批 100 题上跑一组完整历史的 agent，就能变成配对结果

| patch 一次通过 | 107/122 |
| 单次调用最高 token | 15,414，没有一次超过 16K |

| 每题步数 | 平均 14.5 |

**压缩后几乎没有重复工作。** 每次压缩后的 10 个动作里，877 个动作只有 3 个（0.34%，覆盖 72 道题）重复了压缩前的命令，并且中间仓库没有任何改动

分仓库：django 40/46、sympy 13/15、scikit-learn 6/6、sphinx 6/9、matplotlib 4/7、astropy 4/5、pytest 4/4、xarray 3/4、requests 2/2、pylint 0/2

## 8 道溢出题

8 道题以 `ContextOverflow` 结束，其中 3 道靠 harness 在停止时提交的当前 diff 仍然解决。8 道题的原因相同：第一次 patch 被拒后，重试请求要带上被拒的回复（900 到 1,800 token）和错误信息，放不进 16K，于是还没回退成文本交接就终止了。冒烟阶段 36 次 patch 全部一次通过，从未走到重试，所以这条路径是在正式集上才第一次走到。正式结果按冻结时的样子保留

第一次 patch 被拒的原因（用 `--overflow-causes` 离线复现）：

| 原因 | 题数 |
| --- | --- |
| 恢复 stale 事实时，没有比改动更新的证据 | 5（3 道引用的正是做出改动的那一步，2 道只引用了更早的事件） |
| 第一次压缩时 `done_when` 为空 | 1 |
| 状态超过 3K 上限 | 1 |
| 重建时 JSON 格式错误 | 1 |

引用改动那一步的 3 道题说明恢复规则可能过严：改文件的那个动作本身就证明了文件现在的内容。只引用更早事件的 2 道题被拒是对的

## 这 8 道题上的 16K 与 24K

把这 8 道题只改预算，用 24K/18K 重跑（`configs/group_c_24k.yaml`，运行前登记）

| | 16K/12K | 24K/18K |
| --- | --- | --- |
| 解决 | 3/8（全部来自代为提交的 diff） | 6/8 |
| 溢出 | 8 | 0 |
| 压缩 | | 13 次：12 次 patch 一次通过，1 次回退且之后完成 |
| 最高 token | 15,331 | 22,576 |
| 费用 | | $3.91 |

在 24K 下，重试和回退都有空间，流程正常走完：`sphinx-doc__sphinx-9461` 两次 patch 被拒后回退为文本交接，最终解决。也有一道反过来（`sympy__sympy-13091` 在 16K 下靠代为提交的 diff 解决，24K 下没有），属于单次运行的波动

这 8 道题是因为在 16K 下失败才被挑出来的，所以不能代表 24K 在全部样本上的表现。要正式比较 16K 和 24K，需要用 24K 跑完全部 100 题

## 调参中改了什么

所有改动都来自两道试跑题和 20 道冒烟题，没有一项依据正式集，每项都和依据的数据一起登记在方案里：

- token 估算以 API 返回的输入数为锚点；本地 tokenizer 少算聊天格式开销，最多偏低 7.7%
- 压缩轮用剩下的空间（与论文一致），不再要求至少 3K；原规则在第一次压缩时就溢出
- 必要时缩短每一步的输出，保证下一次压缩放得下；普通回复也为它留出空间
- 每个输出上限再留 300 token 安全余量

## 局限

- 每题只跑一次，只测一个模型、一个 benchmark、100 道题
- 没有运行基线，方案里的配对假设没有检验
- 重试空间的缺陷和恢复规则的问题是在正式集上发现的；修复后的效果要在新题上测，不能在这批题上重跑
- `hist` 几乎没被用到，所以这次运行对"按需检索"说明不了什么

## 下一步

- 用 24K/18K 跑完全部 100 道正式题，做配对的 16K 与 24K 对比
- 修复重试路径（重试放不下时直接回退），并接受做出改动的那一步作为恢复证据，然后在 100 道没用过的题上测，作为事后改进版本单独报告
